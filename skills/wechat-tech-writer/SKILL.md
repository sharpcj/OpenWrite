# OpenWrite · 微信公众号技术文章写作助手

## Agent 运行约定

在 OpenWrite 项目中，由根目录 `AGENT_GUIDE.md` 调度本技能。当前文章位于 `articles/<文章目录>/`；所有正文、封面、配图及 HTML 保存到该目录，不写入技能目录。项目任务优先采用用户指定的文章目录；未指定时创建新目录。

本技能属于 **OpenWrite**，不依赖特定 Agent 的工具名或安装目录。

写作约束以任务的角色预设为准：`process/brief.md` 的「写作约束（角色预设）」与 `workflow.json.writer_profile` 快照（来自 `writer_roles/tech.yaml`）优先于本 Skill 的通用建议（含篇幅与配图密度）；预设调整时按新预设执行。

- 使用宿主提供的搜索、网页读取和文件读写能力；文中的动作描述不是固定工具 API。
- `references/` 路径相对于本技能目录；文章和配图需求使用明确的文章目录路径。
- 根据任务使用所需能力：缺少搜索能力时可使用用户提供的资料，并说明无法核实的内容；缺少文件写入能力时提供正文与配图需求内容，不声称已经保存。
- 本技能只定义配图需求和验收规则。项目流程负责将需求交给独立图片能力，再把实际图片结果交回本技能验收。
- 只有收到实际图片结果并通过视觉验收后，才可将其视为完成。尚未取得图片时，在需求与待办中记录，不伪造文件路径或声称完整交付。
- 配图需求写入当前文章目录的 `image-requests.json`，字段约定见 [配图交接协议](../../docs/image-contract.md)。流程产物与提交方法遵循 [七步工作流](../../docs/workflow.md)。不在需求中指定模型、接口或密钥；来源偏好可用 `preferred_sources` 声明。封面为 `cover.png`，单独上传，不嵌入正文。


## ⚠️ 核心原则

### 必须严格遵守的6个要点

1. **🎯 封面图是强制要求**
   - 每篇文章必须生成一张吸引人的主题封面图
   - 封面图**不嵌入 Markdown 正文**，文件命名 `cover.png` 与文章 .md 同目录，发布时由 `publisher.py --cover cover.png` 单独上传

2. **📝 标题简洁有吸引力**
   - 公众号标题不能太长太啰嗦，需要具备吸引力，让读者有兴趣点开
   - 避免平铺直叙的陈述句，用悬念、数字、对比、提问等方式增加点击欲
   - 示例：❌「Claude Agent SDK 的功能介绍与使用指南」→ ✅「Claude Agent SDK：AI 真正的生产力开关」
   - 标题在 Markdown 中用 `#` 写出，格式化时会被移除（公众号后台单独填写），但写作时仍需认真拟定

3. **图片文字语言**
   - 图片中的文字根据内容和场景选择合适的语言，不强制使用中文
   - 面向中文读者的公众号文章，优先使用中文；涉及代码、术语、品牌名等可保留原文

4. **文章只输出正文**
   - ❌ 禁止添加："参考资料"、"图片说明"、"优缺点说明"等章节
   - ✅ 只保留：标题 + 正文 + 结尾总结

5. **链接使用纯文本格式**
   - ❌ 错误：`[官网](https://example.com/)`
   - ✅ 正确：`官方网站：https://example.com/`

6. **流程与板书配图必须清晰准确**
   - 步骤、编号、文字和连接关系必须可读且与正文一致
   - 不满足要求时不使用该图，避免图片误导读者

## 完整工作流程

**搜索资料 → 分析资料 → 写正文 → 生成封面 → 按需生成正文配图 → 生成 Markdown → 排版并保存可发布产物**

三种写作视角都按上述七步执行。选题理解并入搜索资料前的准备；不另增流程步骤。第 3 步先经过标题与大纲检查点，取得用户确认后将完整正文保存为 `draft.md`（不嵌入图片）；第 6 步由项目控制器整合生成 `article.md`；第 7 步由 `openwrite.py format` 生成 `article.html` 与 `publish-manifest.json`，交付可发布产物。中途如需暂存草稿，应在 `brief.md` 标明未完成阶段，不将暂存视为最终交付。正文配图可为零张，内容结构图也按需决定，不强制生成。


### 步骤 1：搜索资料

#### 搜索准备：理解需求并规划

当用户输入一个话题后，首先：

1. **明确主题类型**
   - AI大模型：功能特点、使用场景、与竞品对比
   - 开源工具：核心功能、安装使用、应用案例
   - 技术概念：原理解释、实际应用、发展趋势
   - 新闻资讯：事件背景、影响分析、行业反应

2. **确定文章角度**
   - 新闻类：时效性 + 全面性
   - 介绍类：通俗性 + 实用性
   - 评测类：客观性 + 数据性
   - 教程类：可操作性 + 详细性

#### 搜索内容源

使用当前 Agent 的网页搜索能力进行3-5轮搜索：

**搜索策略**：
- **第1轮**：官方信息（"{产品名} 官方文档"、"{产品名} GitHub"）
- **第2轮**：技术解析（"{产品名} 详细介绍"、"{产品名} 教程"）
- **第3轮**：对比评测（"{产品名} vs {竞品}"、"{产品名} 评测"）
- **第4轮**：补充验证（根据前3轮结果补充缺失信息）

**质量标准**：优先选择官方文档、知名技术博客、权威媒体报道

---

### 步骤 2：分析资料

使用当前 Agent 的网页提取或浏览器能力获取2-5篇代表性文章的完整内容：

**优先级**：
1. 官方文档或官方博客（权威性）
2. 技术博客：掘金、CSDN、Medium（深度）
3. GitHub README.md（实用性）
4. 权威媒体技术报道（全面性）

**提取要点**：
- 核心功能和特性
- 技术原理（简化版）
- 使用场景和案例
- 优势和局限性
- 最新动态和发展方向

对照来源核实关键事实和数据，区分已证实信息、个人判断与待确认内容，再提炼文章核心观点。

---

### 步骤 3：写正文

**先经过标题与大纲检查点**（除非任务已授权跳过）：给出三个备选标题——至少一个激进、有悬念、吸引点击的（标注 `激进悬念`），一个相对客观中性的（`客观中性`），第三个默认利益实用型（`利益实用`）——同时列出大纲，请用户选定标题（可自定义）并确认大纲。用户可反复提修改意见，每轮更新 `outline.md`，确认前不生成全文；确认结果写入 `outline.json`。`draft.md` 的 H1 必须与已确认标题一致。

**核心原则**：
- 用自己的语言重新组织，绝不照搬原文
- 面向普通用户，避免过度技术化
- 增加生动的比喻和实例
- 保持事实准确性

**推荐文章结构**（1000-1800字，角色预设可调整）：

```
1. 引子（100-150字）
   用一个场景或问题引入话题

2. 是什么（200-350字）
   产品/技术的基本介绍
   用类比帮助理解核心概念

3. 能做什么（300-550字）
   核心功能特性
   实际应用场景
   具体使用案例

4. 为什么选择它（200-350字）
   独特优势
   与同类产品对比

5. 如何开始（150-250字）
   快速上手指引
   提供官方资源链接（纯文本格式）

6. 总结（100-150字）
   总结要点
   展望未来
```

**语言风格**：
- 使用"我们"、"你"等第二人称，增加亲切感
- 适当使用emoji（但不要过度）
- 短句优于长句（不超过25字）
- 多用并列结构和小标题

**详细写作指南**：参见 [references/writing-style.md](references/writing-style.md)

### 步骤 4：生成封面

**⚠️ 这是强制步骤**：每篇文章必须生成一张吸引人的主题封面图。

#### 快速开始

**核心要点**：
- 根据主题选择配色：AI类用蓝紫渐变、工具类用绿橙渐变、效率类用橙粉渐变
- 标题：主题关键词（中英文结合）
- 副标题：一句话核心价值（简体中文）
- 视觉元素：与主题相关的3D元素、光效、粒子

**配图需求与验收**：

- 封面尺寸：1024×432，比例约 2.35:1。
- 根据正文主题确定画面焦点、配色和构图；在 `image-requests.json` 中定义 `cover` 需求，输出文件为 `cover.png`。
- 封面采用**底图 + 标题叠字**：底图不渲染文字（`text` 置空），标题/副标题写入 `overlay` 对象，由图片能力用 Pillow 精确排版。`overlay.title` 必须使用已确认的文章标题（控制器校验一致性），`subtitle` 为一句话核心价值；构图给叠字留白（默认左下）。
- 不允许图片编造数据；区分正文中的事实和装饰性视觉元素。
- 项目流程将需求交给独立图片能力；本技能评估来源偏好（`preferred_sources`），不选择实现方式、不调用图片后端。
- 图片返回后，检查主题契合、尺寸、叠字完整清晰、色调及构图。未通过时说明需要调整的设计要求，再由项目流程安排处理。

**质量验证清单**：
- [ ] 中文文字清晰可读，无乱码
- [ ] 颜色鲜明，吸引眼球
- [ ] 视觉重点突出（标题最醒目）
- [ ] 整体符合主题

#### 详细指南

**完整的封面图设计原则、设计描述模板、验收方法**：

👉 **参见** [references/cover-image-guide.md](references/cover-image-guide.md)

包含：
- 5类文章的配色方案
- 5个提示词模板（AI类、工具类、效率类、新闻类、教程类）
- 详细的设计步骤和质量验证方法
- 常见问题排查

### 步骤 5：按需生成正文配图

**⚠️ 这是可选步骤**：根据文章内容判断是否需要配图，按需生成，不设数量上限。但注意配图不要太密，通常每个 H2 章节最多 1 张。

**来源评估**：提交需求前按内容评估适合的来源，用 `preferred_sources` 声明（缺省按默认优先级）。与官方文档内容强相关的插图（架构图、界面截图、官方图表等），优先搜索并下载官方文档对应原图，把本地路径写入 `source_file`、原始链接写入 `source_url`，以 `file` 来源导入；找不到时按 本地 ComfyUI > 免费图库 > 在线生图 回退。使用图库时提供 `keywords`。评估与声明由写作侧完成，实际获取与回退由图片能力执行。

#### 配图体系：Type × Style

内容配图采用 Type（画面构成）× Style（视觉风格）体系：

- **Type** 决定「画什么」：12 种类型，见 [references/image-styles/styles.md](references/image-styles/styles.md)
- **Style** 决定「什么风格」：9 种视觉风格，Agent 根据文章调性自动选择
- **自动推荐**：根据文章内容信号自动匹配 Type + Style，见 [references/image-styles/auto-selection.md](references/image-styles/auto-selection.md)
- **风格预设**：按文章类型预置组合，见 [references/image-styles/style-presets.md](references/image-styles/style-presets.md)

#### 决策规则

```
阅读文章内容
  │
  ├─ 有明确数据对比？ → comparison（对比说明）
  ├─ 有复杂技术架构？ → architecture（架构图）
  ├─ 有抽象概念/原理？ → concept（概念讲解）
  ├─ 有教程/步骤？     → process（流程步骤）（步骤与连接关系必须准确清晰）
  ├─ 有知识框架？      → mindmap（思维导图）
  ├─ 有发展历程？      → timeline（时间线）
  ├─ 有Tips/要点？     → checklist（清单图）
  ├─ 有核心金句？      → quote-card（金句卡片）
  └─ 其他情况          → 不生成配图
```

#### 配图数量

根据文章内容按需生成，不设硬性上限。原则：

- 每个 H2 章节最多配 1 张图
- 纯文字叙述、没有可视化价值的段落不配图
- 配图密度参考：1000-1800 字文章通常 1-3 张
- 宁缺毋滥：不确定是否需要的，不配

#### Prompt 构建

每种 Type 有专用 prompt 模板，见 [references/image-styles/prompt-construction.md](references/image-styles/prompt-construction.md)。

**关键原则**：
- 图片内文字根据内容和场景选择语言，prompt 中直接写出要显示的文字
- 一图一个焦点，不要塞太多元素
- 用文章中的真实数据，不要 placeholder
- 抽象优于具象：「AI 赋能」→ 光线连接感 ✅，不要画机器人 ❌

#### 正文配图需求

正文配图尺寸为 1024×768（4:3）。在 `image-requests.json` 中记录图的类型、风格、色调、构图、文字、真实数据和插入位置，由项目流程取得图片。返回后对照正文验收，确认实际文件存在再引用。

---

### 步骤 6：生成 Markdown

封面和正文配图处理完毕后，由项目流程运行 `workflow finalize`，根据 `draft.md` 与已验收正文图片需求整合生成 `article.md`。没有正文配图时保留纯正文；封面不写入 Markdown。

### 步骤 7：生成可发布交付件

运行 `python3 openwrite.py format <目录> --theme default`，由项目入口调用排版能力生成 `article.html`，执行可发布性检查（标题/作者/摘要长度、封面格式与大小、代码块转换、本地图片齐备），写入 `publish-manifest.json` 并自动完成第七步。检查不通过时保留上一次成功的 HTML，不推进状态。七步完成即交付可发布产物；上传草稿仍需用户明确确认。

文章文件示例：

**文件内容结构**：
```markdown
# 文章标题

## 第一部分标题

正文内容...

![配图1](comparison.png)  <!-- 如有内容配图 -->

*图：简短说明*

## 第二部分标题

正文内容...

## 总结

结尾总结段落...
```

**重要提醒**：
- ❌ 不要添加"参考资料"、"图片说明"、"延伸阅读"等额外章节
- ❌ 不要使用markdown超链接格式 `[文本](URL)`
- ❌ 不要在 Markdown 里写封面图（如 `![](cover.png)`），封面图发布时单独上传
- ✅ 只输出：标题 + 正文 + 总结
- ✅ 链接使用纯文本格式：`官方网站：https://example.com/`

**输出文件**：
- 文章文件：当前文章目录中的 `article.md`
- 封面图：`cover.png`
- 内容配图（如有）：`performance-comparison.png`、`architecture.png`等

## 质量检查清单

在输出前务必确认：

### 内容质量
- [ ] 内容完全用自己的语言表达，无大段照搬
- [ ] 技术术语有通俗解释
- [ ] 包含具体例子和应用场景
- [ ] 事实信息准确无误
- [ ] 文章结构清晰，易于阅读
- [ ] 语言自然流畅，适合公众号风格
- [ ] 字数在1000-1800字之间（以角色预设为准）

### 图片质量（强制检查）
- [ ] ✅ **已生成主题封面图**（强制要求）
- [ ] 封面图颜色鲜明，有吸引力
- [ ] 封面图中文文字清晰可读，无乱码
- [ ] 封面图视觉重点突出，符合主题
- [ ] 内容配图（如有）数据准确
- [ ] 所有图片已保存到输出目录
- [ ] 图片风格统一（配色、设计风格一致）

### 格式规范
- [ ] 封面图 `cover.png` 已生成并保存到文章同目录，但**未写入 Markdown**（发布时由 `--cover` 上传）
- [ ] 链接使用纯文本格式（不是markdown超链接）
- [ ] 没有添加"参考资料"、"图片说明"等额外章节

用户输入话题
  │
  ├─ 包含"最新"、"发布"、"更名" → 新闻资讯类

## 注意事项

### ✅ 应该做的

1. **每次都生成封面图** - 这是强制要求，不可省略
2. **验证中文清晰度** - 生成后检查文字是否清晰
3. **控制图片数量** - 按需配图，每个 H2 章节最多 1 张，宁缺毋滥
4. **保持风格统一** - 如有多张配图，配色和设计语言要一致
5. **链接用纯文本** - 不使用markdown超链接格式

### ❌ 不应该做的

1. **不要跳过封面图** - 即使时间紧也必须生成
2. **不要过度配图** - 宁缺毋滥，没价值的图不生成
3. **不要照搬原文** - 必须用自己的语言改写
4. **不要添加额外章节** - 如"参考资料"、"图片说明"
5. **不要忽视质量检查** - 输出前必须过一遍检查清单

## 提升质量的关键点

1. **选题要精准**：理解用户真正想了解什么
2. **信息要准确**：事实和数据必须可靠
3. **语言要通俗**：技术术语要解释，多用比喻
4. **结构要清晰**：小标题、列表、图表帮助阅读
5. **封面要吸睛**：配色鲜明、标题醒目、主题契合
